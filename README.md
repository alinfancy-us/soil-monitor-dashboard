# SoilPulse Web Dashboard (soil-monitor-dashboard)

The official web dashboard for the SoilPulse soil temperature & moisture sensor. Fully static (`index.html` + `page/`) — no app install and no backend required: the browser connects directly to the device's GATT service (random 128-bit UUID `749b53b7-2662-4658-9fb4-e47241816727`, advertised in the scan response) over the **Web Bluetooth API** for live readings, history / daily-average charts, sensor calibration, temperature offset, device naming, firmware OTA updates, and factory reset.

Live: <https://soilpulse.alinfancy.com>

## 1. Features

| Module | Description |
| --- | --- |
| 📊 Data | Live temperature (°F/°C toggle), moisture and battery readings; 24 h trend chart (144 × 600 s samples over `0xFFEC`, newest page first + background backfill) and a 7-day / 30-day daily average chart; measurement history table (cached in localStorage) |
| 📘 Guide | Quick start: battery installation, planting depth, Web Dashboard / Home Assistant setup, troubleshooting, FCC statement |
| ⚙️ Setting | Two-point moisture calibration (dry 0% / wet 100%), temperature offset (-10 ℃ to +10 ℃, 0.5 ℃ steps), device display name (≤ 20 bytes printable ASCII), firmware OTA update, factory reset & reboot |
| Global tools | Connect device, Refresh (triggers an immediate measurement), Clear data (clears the local cache + on-device history) |

Browser support: Web Bluetooth requires a **secure context (HTTPS or localhost)**. Use Chrome or Edge on Android / Windows / macOS. On iOS / iPadOS neither Safari nor Chrome supports Web Bluetooth — the page automatically shows a dialog guiding users to the **Bluefy** browser (with a deep link that opens this dashboard directly).

## 3. Local development

```bash
cd soil_monitor_dashboard
python3 -m http.server 8000
# Open http://localhost:8000 (localhost is a secure context, so Web Bluetooth works)
```

Or run `./start_service.sh`: serves on local port 8000 and opens a random public HTTPS tunnel via ngrok — handy for testing on a real phone.

Styling (Tailwind):

- Styles are compiled at build time (no CDN runtime script): `./build_css.sh` compiles `tailwind.input.css` + `tailwind.config.js` into the committed `page/css/tailwind.css`.
- **After changing any class names in `index.html` or `page/js/**`, rerun `./build_css.sh` and commit the regenerated CSS** — otherwise the new styles never ship. CI reruns the build as a safety net, but keep the committed artifact in sync.

Debugging tips:

- BLE traffic logs are gated by `DEBUG_ENABLED` in `page/js/config.js` (currently `true`); messages appear in the browser console with the `[SoilPulse]` prefix.
- The footer shows the frontend version (`PAGE_VERSION`) so you can confirm which build the browser actually loaded.

## 4. Versioning & cache busting

- `PAGE_VERSION` in `page/js/config.js` is the frontend version, shown in the page footer for cache troubleshooting.
- The three business scripts at the bottom of `index.html` (`config.js` / `ble-protocol.js` / `app.js`) share **one unified `?v=` version** for cache busting — they are always released together and must never drift.
- On CI the version is synced automatically from a single source of truth: `deploy.yml` (production, git tag, e.g. `v1.3.20` → `1.3.20`) and `dev.yml` (GitHub Pages preview, current commit short hash) rewrite both `PAGE_VERSION` and the three `?v=` values in `index.html` — no manual sync needed.
- For local development, bump the same version in `config.js` `PAGE_VERSION` and all three `?v=` values in `index.html` whenever any JS changes, otherwise browsers keep running the old JS.

## 6. GATT protocol quick reference

Service `749b53b7-2662-4658-9fb4-e47241816727` (random 128-bit, carried in the BLE scan response packet); characteristic definitions live in `page/js/config.js` and must stay in sync with `app_att.h` in the firmware repo.

| Characteristic | Ops | Purpose |
| --- | --- | --- |
| `0xFFE1` | Read / Notify | Measurement data (timestamp / temperature / moisture / battery) and the last-5-record history packet |
| `0xFFE2` | Write | 4-byte Unix timestamp to sync the device clock |
| `0xFFE3` | Read | 7-day daily averages (`count` + 7 × daily record) |
| `0xFFE5` | Write | Clear on-device history (magic `CLR1`) / factory reset & reboot (magic `RST1`) |
| `0xFFE6` | Write | Two-point moisture calibration (`0` = dry, `1` = wet; the device first measures the current probe state, then applies calibration from that fresh sample) |
| `0xFFE7` | Write | Trigger an immediate measurement (Refresh button) |
| `0xFFE8` | Read / Write | Temperature offset (s8, 0.1 ℃ units, ±10 ℃ range) |
| `0xFFE9` | Read | Calibration status flags (bit0 dry / bit1 wet / bit2 non-zero temperature offset) |
| `0xFFEA` | Read / Write | Device display name (≤ 20 bytes printable ASCII, dashboard display only) |
| `0xFFEB` | Read / Notify | Latest measurement (timestamp / temperature / moisture / battery / monotonic `measure_seq`) — the live card and the Refresh result |
| `0xFFEC` | Read / Write | 24 h history block read: write a 2-byte `{offset, count}` window, then read a 183-byte block (`total, offset, count` + up to 20 × 9-byte records, clamped so it fits one MTU-185 read); the page fetches the newest page first and backfills older pages in the background |
| `0x180A` / `0x2A26` | Read | Standard Device Information Service, firmware revision (compared against the update manifest) |
| Telink OTA service | Write | Firmware transfer (dual-bank; the previous firmware keeps running if an update fails) |

> The advertised name is fixed to `SoilPulse` (used for `requestDevice` filtering). `0xFFEA` only changes the name shown on this dashboard — the phone's Bluetooth list keeps the built-in name, and nothing needs to be re-paired in Home Assistant.

### Clock sync and the stale history tail

The page always writes `0xFFE2` right after connecting, so the device gets a real time base before history is read. Two firmware behaviours follow from that, and both are expected:

- **Before the first sync, samples never reach flash.** The device keeps them in a 144-record SRAM ring (≈ 24 h at the 600 s cadence) and refuses to write anything with an unknown timestamp. The 24 h curve can therefore be empty, or stop at the last session, until a sync happens — those points have no trustworthy absolute time. A power loss discards whatever is still buffered.
- **The sync schedules a one-shot backfill** into the flash log (up to 144 records, ~30–70 ms), executed by the device main loop because an ATT callback must not erase flash. If the first `0xFFEC` read wins that race, the newest history point is older than the Latest card even though its timestamp is valid, so the usual "drop invalid timestamps" filter cannot notice.

One silent fallback covers that race: when the Latest timestamp is more than **60 s** ahead of the newest history point, the page re-fetches the whole history after 600 ms (max 2 attempts, on the same global `gattOp` lock) and stops immediately if the tail did not advance. It must be a full re-fetch, never an extra last page — `0xFFEC` only exports the newest 144 records, so after a backfill `total` grows and the offset base shifts, and appending a page would duplicate or skip points. `state.lastRecords` is cleared and the backfill job object replaced first, so stale points do not linger and in-flight paging stops. The attempt is cancelled on disconnect, Clear or device switch; look for `[TIME] tail stale` / `[TIME] tail recheck` in the console.

Normal rounds never trigger it: a sampled round updates the Latest value and the history record with the same timestamp, so the lag is 0 (fast rounds that skip the history write stay far below the threshold). The only false positive is a reconnect after pressing Refresh, since Refresh updates the Latest value only — which is exactly what the "did the tail advance?" check catches.

### Duplicate points with shifted timestamps

Older firmware stored `uptime` in the ring and converted it to an absolute epoch **at export time**. Because the page writes `0xFFE2` on every connection, the base can move by tens of seconds, so the same measurement came back at two different times: once from `0xFFEC` (flash, written under the old base) and again from a later `0xFFE1` poll (re-converted with the new base). The cache then held pairs of records with identical `temp`/`hum`/`batt` and timestamps 41–53 s apart, which looked like duplicated points and pushed real history out of the 144-record cap.

Two layers now prevent it:

- **Firmware (root fix):** each ring slot freezes its epoch when the record is pushed, so re-syncing the clock only affects new samples. `0xFFE1`, `0xFFEB` and the `0xFFEC` RAM fallback all read the frozen value. Upgrading requires **one `CLR1`** to drop the `ts = 0` records left by old firmware.
- **Page (backstop):** `mergeTrendRecords()` still merges records within **2 s** (device-side drift, later value wins), and additionally treats two records as the same point when `temp`, `hum` and `batt` are **all equal** and they are **≤ 60 s** apart — keeping the **earlier** timestamp (the flash truth). Normal 600 s sampling and 30 s fast rounds cannot collide: three quantised values matching exactly one minute apart is effectively impossible.

`test/e2e/run-history-dedupe.mjs` injects `duplicateShiftS: 53` into the fake device's history and asserts the cache ends up with exactly the physical sample count, no same-value pairs within 60 s, and ascending timestamps. No cache migration is performed — the dedupe runs on every `render()`, so old caches are cleaned the first time the page loads.

## 7. Keeping in sync with the firmware repo

- Constants such as the GATT UUIDs, the advertised name prefix, calibration command values and the temperature offset range (±10 ℃) must match `bth_soil_sensor/app_att.h` and `app_config.h` in the firmware repo; always change both sides together, otherwise the dashboard cannot connect or writes invalid parameters.
- The `0xFFEC` window/block layout (183 B response, ≤ 20 records per block, `offset ≥ total` = end of transfer) is driven by the firmware's MTU-185 read limit, and the tail-stale thresholds are tuned against `SOIL_HISTORY_MAX = 144` / `SOIL_SAMPLE_PERIOD_S = 600`; change them together with `soil_hourly.h` and `app_config.h`.
- Firmware release flow: publish a Release in the firmware repo (asset named `SoilPulse_v<version>.bin`) → this repo's production pipeline fetches it via `FW_TAG` and attaches it to the `page/firmware/firmware.json` manifest → after connecting, the page compares versions automatically and prompts a one-tap OTA update.
